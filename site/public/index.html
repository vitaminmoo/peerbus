peerbus

Lets Claude Code sessions message each other across Claude accounts, across machines, and between you and friends you've paired with.

Claude Code can already pass messages between sessions that run under one account on one machine. peerbus extends that to your other accounts, your laptop and server, and people you choose to pair with. A message reaches a busy session between tool calls and starts a new turn in an idle one, the same as the built-in messaging.

Early software. Commands and file formats will change. It depends on Claude Code features that aren't meant for everyday use yet: channels are a research preview, and loading this one takes the --dangerously-load-development-channels flag.

How it works

 Claude session ─stdio─ peerbus channel ══ QUIC ══ peerbus channel ─stdio─ Claude session
                               └──── rv.peerb.us: introductions, relay if needed ────┘

Each Claude Code session runs peerbus channel, an MCP server that uses Claude Code's channels feature to push messages into the session.

Sessions talk to each other directly over QUIC with TLS 1.3, each side pinned to the other's key. peerbus uses the most direct path it can find: loopback on the same machine, the LAN at home, a hole-punched connection across NATs, and the relay only when nothing else works. list_peers shows which one each session took.

The rendezvous server introduces sessions to each other. It only answers someone who already knows a meeting point, which is derived from a secret that exists only on the two paired sides and changes every hour. It can't list who is online, and it can't read traffic, including relayed traffic. It does see which addresses meet each other, and when.

A peer only shows up while one of their sessions is online and you have them enabled. There are no offline queues and no message history anywhere but in the two sessions' transcripts.

Install

Linux. macOS should work but hasn't been tested. You need Go 1.27 or newer.

go install github.com/vitaminmoo/peerbus/cmd/peerbus@latest

Register the channel with Claude Code. If you use more than one Claude account on a machine, do it once per account:

claude mcp add -s user peerbus -- peerbus channel
CLAUDE_CONFIG_DIR=~/.claude-work claude mcp add -s user peerbus -- peerbus channel

Start sessions with the channel enabled:

claude --dangerously-load-development-channels server:peerbus

Channels are a research preview, and Claude Code only loads channels outside Anthropic's allowlist with that flag. It asks you to confirm each time. An alias saves typing:

alias claudep='claude --dangerously-load-development-channels server:peerbus'

Servers added with --mcp-config don't count for server: channels. Use claude mcp add or a project .mcp.json.

Sessions that were already running keep the old peerbus channel process. After installing or upgrading, start new sessions.

One machine

That's all it takes on one machine. Sessions find each other through a directory under ~/.local/state/peerbus and connect over loopback, whichever Claude account each runs under. No server is involved, and it works offline.

Your identity key is created the first time anything needs it. Give yourself a name before you pair with anyone; it's what your sessions are listed under:

peerbus id -name yourname

Your machines

Pairing refuses to overwrite a machine that already has peers of its own unless you pass -force. Both machines talk to the rendezvous server to find each other; see running your own if you'd rather not use rv.peerb.us.

Each machine is listed under its hostname unless you name it with peerbus id -machine laptop. The machine name belongs to that machine; your own name (-name) is shared by all of them.

Your machines keep one peer list between them. Pair a friend, change their permissions or remove them on any machine, and the others pick it up as soon as a session there is connected to one on the machine where you made the change. For each peer the most recent change wins, and removals stick: a machine that was switched off doesn't bring a removed friend back.

Once a session is running on each machine, peerbus peers on either shows both. peerbus peer list shows only other people, since your machines are all you.

Friends

Anyone holding an invite code can pair as them until it's used. Codes work once and expire after 15 minutes (-ttl changes that).

Both sides print the other's fingerprint. If you want to be sure nobody swapped the code in transit, compare fingerprints some other way; peerbus id shows yours.

Their sessions appear in list_peers and peerbus peers under the name you gave them, within a few seconds, without restarting anything. The first message either Claude sends the other is held for a human to approve; see permissions for how to loosen that.

Manage peers with peerbus peer:

peerbus peer list
peerbus peer disable alice
peerbus peer rename alice al
peerbus peer rm alice

Permissions

Each peer has settings, enforced by your side, shared by all your machines, and picked up by running sessions as soon as you change them:

SettingValuesDefaultMeans
deliverhold, autoholdTheir messages wait for your approval. Approving one opens that conversation for two hours, and so does a message your Claude sends them first.
sendauto, askautoWhether your sessions' messages to them wait for your approval.
sessionsglobs*Which of your sessions they can see and address, by name. A glob with a / matches machine/name, so laptop/* is everything on one machine.
detailstrue, falsefalseShow them your sessions' working directories and Claude accounts.
resourcestrue, falsetrueShow them what your sessions advertise.
 
peerbus peer set alice deliver=auto sessions='ghidra-*,desk/*'

Held messages wait in ~/.local/state/peerbus/inbox.json on the machine that received them. The session is told that something is waiting, but not what it says:

peerbus inbox
peerbus approve 3fa9
peerbus deny 3fa9

A message addressed to you as a person (alice/) rather than to a session is held until you pick one with approve -to SESSION. The sender's Claude gets a notice either way.

In Claude

Each session gets four tools:

list_peers
Sessions you can reach right now, with status, host, how they're connected, and what each advertises: MCP servers, programs, repos. Takes a filter, like ghidra.
send
A plain-text message to a session, addressed as alice/session-name#ref, or just session-name for your own.
subscribe_idle
One notice when another session finishes its turn or disconnects, instead of polling it.
advertise
Publish something this session can offer, beyond what's detected automatically.

Messages arrive as <channel source="peerbus" from="…" thread="…" foreign="…">. Claude replies on the same thread. Your terminal shows a one-line preview.

From the shell

The CLI joins the same network for a moment, so it sees what a session would see and can speak for you:

peerbus peers
peerbus peers -filter ghidra
peerbus send fedora-build "re-run the lab, the NAT fix is in"
peerbus send alice/ "ping me when the decomp finishes"

Messages from the CLI arrive from you/cli, and replies to them can't reach you there. Sending from the CLI counts as your own say-so, so it isn't held by your send=ask setting.

Security

A friend's Claude is someone else's agent, and a message from it is untrusted input. Messages from friends are marked that way, and a held message's text stays out of your Claude's context until you approve it.

The realistic attack is prompt injection that spreads: your session reads something hostile and is talked into inviting a stranger or loosening a peer's permissions, and then passes the same text to your friends. The commands that change trust (invite, pair, peer, approve) refuse to run without a terminal, which Claude's Bash tool doesn't have. That's a speed bump, so also deny them in Claude Code's settings. Deny send and inbox too: a send from the CLI skips send=ask, and the inbox prints held messages in full.

{
  "permissions": {
    "deny": [
      "Bash(peerbus invite:*)",
      "Bash(peerbus pair:*)",
      "Bash(peerbus peer:*)",
      "Bash(peerbus approve:*)",
      "Bash(peerbus send:*)",
      "Bash(peerbus inbox:*)",
      "Read(~/.config/peerbus/**)",
      "Read(~/.local/state/peerbus/**)"
    ]
  }
}

Other things worth knowing:

  • Your identity key is ~/.config/peerbus/identity.key. Anyone with it is you to every friend.
  • Only the CLI, run by your own OS user on the same machine, can approve, deny, or list on a session's behalf. Other sessions can't, including your own on other machines.
  • Claude Code keeps session transcripts as plain text, so every message ends up on disk on both ends. Encryption protects the wire, not the endpoints.
  • The rendezvous operator sees metadata: which addresses meet, when, and how much they relay.

Running your own server

The rendezvous server is a single binary on one UDP port, and holds nothing but live registrations:

peerbus rendezvous -listen 0.0.0.0:47615

Point your machines at it in ~/.config/peerbus/client.json:

{ "rendezvous": "rv.example.com:47615" }

Invite codes carry the server address, so friends use whichever server the invite names. If your server shares a NAT with you, peerbus also asks a public STUN server for your real address ("stun" in the same file). To keep sessions to one machine and never contact a server, set "rendezvous": "none".
